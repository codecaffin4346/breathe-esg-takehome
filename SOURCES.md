# Sources and Real-World Formats

We didn't invent clean data for this prototype. We looked at what actually comes out of enterprise systems.

## 1. SAP (Fuel and Procurement)
**What we researched:** SAP exposes data via IDocs, BAPIs, OData, and simple ALV grid exports. While OData is standard in S/4HANA, the reality of many enterprise ESG integrations is dealing with flat-file CSV dumps from older ECC systems, often generated by a background job (e.g., transaction ME2N for purchasing).
**What we learned:** SAP German defaults often leak into column headers if the system language isn't strictly enforced. You rarely get a clean "Unit" column; you get `MEins` (Maßeinheit). You get `Werk` instead of Plant. Dates are often `DD.MM.YYYY`. 
**Our Sample Data:** Our SAP mock file (`sap_export.csv`) uses these exact German headers and tricky date formats.
**What would break in prod:** If a client switches their SAP logon language to English, the headers change to `Quantity` and `Plant`, and our hardcoded parser breaks. In production, we need a configurable column-mapping UI during tenant onboarding.

## 2. Utility Data (Electricity)
**What we researched:** The Green Button standard is the holy grail, providing structured XML (ESPI). However, many utilities provide a simpler CSV "Download My Data" option, or a generic portal scrape.
**What we learned:** Utility CSVs rarely have a single "Date". They have a `Start Date` and `End Date` for the billing period. They also often include "Tiered" pricing lines, meaning a single month might have three rows for the same meter (Tier 1 usage, Tier 2 usage, and fixed charges).
**Our Sample Data:** Our utility mock file (`pg_e_portal.csv`) includes overlapping billing dates (e.g., Jan 10 - Feb 09) and we have to extract just the usage rows, ignoring the cost rows.
**What would break in prod:** Smart meters provide 15-minute interval data. If a client uploads an interval CSV instead of a monthly billing CSV, our system would ingest 2,880 rows per month per meter instead of 1. We need logic to aggregate interval data up to monthly totals.

## 3. Corporate Travel (Navan/Concur)
**What we researched:** We looked at Navan's API and how Concur integrates with Thrust Carbon.
**What we learned:** Travel APIs often provide booking-level data. The tricky part is that sometimes a flight API payload contains the `origin` and `destination` IATA codes (e.g., SFO, LHR), but not the actual flight distance, which is required for accurate DEFRA emission calculations.
**Our Sample Data:** Our travel mock (`travel_api.json`) simulates this. It provides the airports and travel class, but omits distance. 
**What would break in prod:** Our parser currently has a hardcoded mockup for `SFO -> LHR = 8600km`. In production, this requires integration with a geospatial database or an external API (like Google Maps or a flight distance calculator) to resolve the missing distances. If we get a new airport pair, the parser will fail.
